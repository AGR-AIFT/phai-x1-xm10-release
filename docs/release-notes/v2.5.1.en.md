# XM10 Extension Module SDK v2.5.1

> **Release date**: 2026-07-29 | **Target HW**: **Rev 2.0 only** (Rev 1.1 unaffected) | **KIT H10 FW**: v2.3.0+

> ✅ **Verified (2026-07-30)** — shortly after release we received a report that the board "still
> hangs on v2.5.1". Re-investigation showed the cause was **the debugging environment, not the
> firmware** (breakpoints left over from a previous session plus an outdated ST-LINK firmware kept
> interrupts masked during the debug session). **v2.5.1 firmware is confirmed working.**
> If you see the same thing, check the **"Debugging caveats"** section below first.

---

## At a glance

An **urgent fix for Rev 2.0 boards that stopped part-way through boot.** No feature changes.

- **Symptom** — power the board and **the LEDs stay dark, and no COM port (USB serial) shows up on your PC.** The firmware is stuck mid-boot.
- **Affected versions** — **Rev 2.0 firmware of v2.4.1 and v2.5.0.** v2.4.0 and earlier are not affected.
- **Rev 1.1 is unaffected** — the code that caused this never existed on Rev 1.1. Keep using your current build.
- **What to do** — Rev 2.0 users: download **`Rev2.0.zip`**, rebuild, and upload.
- **Bootloader (optional)** — a **newer bootloader build (2026-07-30)** with a stability improvement is attached. The existing bootloader keeps working fine, so this is not required — update when convenient.

---

## What happened? (in plain terms)

The board has a **clock that ticks 1000 times a second**. Whenever the firmware wants to "wait 0.01 seconds", it watches that clock.

Very early in boot there is a short stretch where the firmware says **"don't interrupt me right now"**. That block is supposed to be lifted as soon as the stretch ends — but **the operating system (FreeRTOS) had not started yet, so the code that lifts it did not run.** The "do not disturb" flag stayed on, and the clock never ticked.

That is where it bites. The **first place in boot that ever says "wait a moment" is the USB initialisation** — and with the clock frozen, that wait **never ends.** So the board stops right there.

> USB was not broken. USB just happened to be **the first place that noticed the clock had stopped.**

This release makes sure that "do not disturb" is always lifted when the stretch ends, and adds a second safety net that clears it once more at the very start of boot, in case anything else ever does the same thing.

## Does this affect my board?

| Check | Affected? |
|-------|-----------|
| Board **has an RJ45 Ethernet port** (= Rev 2.0) + firmware is **v2.4.1 or v2.5.0** | **Yes — update to v2.5.1** |
| Board has no RJ45 port (= Rev 1.1) | No — keep using it |
| Rev 2.0 but firmware is **v2.4.0 or earlier** | No (updating is still recommended) |

If your board boots and a COM port appears on your PC, you are not affected.

---

## How to update

1. Download **`Rev2.0.zip`** below and extract it (to a path with no spaces or non-ASCII characters).
2. Open it in STM32CubeIDE and build.
3. Upload with **PhAI Studio USB upload**. The bootloader is already installed — no need to reinstall it.

> If the board is already stuck and PhAI Studio cannot connect, flash it once directly over **SWD (ST-Link)**.

---

## Debugging caveats — "I updated and it still looks stuck"

If the board still appears to hang at the same place after updating to v2.5.1, the cause may be your **debugging environment** rather than the board or the firmware. The reproduction report we received right after release turned out to be exactly this — two things combined:

1. **Upgrade your ST-LINK firmware** — STM32CubeIDE menu `Help → ST-LINK Upgrade`.
   An outdated ST-LINK firmware can keep interrupts masked throughout the debug session, which
   makes perfectly good firmware look as if its 1 ms tick has stopped.
2. **Remove all breakpoints from previous sessions** — `Run → Remove All Breakpoints`.
3. Still stuck? **Unplug every cable, fully power-cycle the board, then connect power only —
   no debugger.** If the LEDs come up and a COM port appears, the firmware is fine.
   (An interrupt mask left behind by a debugger is only cleared by a full power cycle.)
