> **Release date**: 2026-11-08 | **Target boards**: **Rev 2.0 only** (Rev 1.1 stays at v2.8.1) | **New**: CAN communication · CANopen helper functions · IMU Hub sensor calibration · device examples

> 🛑 **Rev 2.0 only** release. The Rev 1.1 SDK has no changes since v2.8.1. If you use a Rev 1.1 board, keep using the `Rev1.1.zip` you already have.
>

## At a glance

- **You can talk to your own device over the CAN-FD #2 port (Rev 2.0).** Register a device number, and XM10 receives that device's data and alive signal for you. You can also send and receive with just an ID and data, without a protocol, and you can switch the port to classic CAN. `xm_api_canbus.h`
- **Helper functions for CANopen motor drivers are new (Rev 2.0).** NMT · heartbeat monitoring · SDO expedited read/write. `xm_api_canopen.h`
- **You can calibrate IMU Hub sensors while they stay mounted (Rev 2.0).** Start and finish the gyro zero, magnetometer and accelerometer calibrations from your own code. `xm_api_imu_calib.h`
- **Device examples are new.** The partner devices for the XM10 examples — an STM32G474 reference device and 2 PC simulators. `device-examples/`
- **Total Data (`0x20`) is 4 bytes bigger (Rev 2.0).** A field for the sensor times of IMU Hub sensors 3 – 5 was added. If Total Data does not show in PhAI Studio, view it with the `xm10` tool in the SDK.
- **Fixes** — Total Data values that wobbled at 50 ms · 5 s intervals · a memory problem when deleting a finished one-shot task · `XM_SetChannelLedRGB(ch, 0, 0, 0)` not behaving as documented · the SDK build failing when you changed the build configuration to Release · `xm_api.h` pulling in names that are not part of the public API.
- **Example count** — Rev 2.0: 52 / Rev 1.1: 40.
- **The firmware version written in the Rev 2.0 SDK is 2.10.0.**

## CAN Communication — Talk to Your Own Device (Rev 2.0)

Connect your own CAN-FD device or classic CAN device to the CAN-FD #2 port (the port that the sensor hubs use).

```c
#include "xm_api.h"

#define MY_DEVICE_ID  (0x20U)

static uint8_t s_seq = 0U;   // command sequence number
static uint8_t s_led = 0U;   // LED value to send to the device

void Control_Setup(void)
{
    XM_CanAttachDevice(MY_DEVICE_ID);                     // register the device number — only inside Control_Setup()
}

void Control_Loop(void)
{
    XmCanFrame_t f;
    if (XM_CanReadLatest(MY_DEVICE_ID, 1, &f)) { /* latest value of the periodic data — use f.seq to tell whether it is new */ }

    const uint8_t cmd[2] = { s_seq, s_led };
    if (XM_CanSend(MY_DEVICE_ID, cmd, sizeof(cmd)) == XM_CAN_OK) { s_seq++; }   // XM_CAN_OK is 0 — always compare with ==
}
```

| Way | Functions |
|------|------|
| Device API — decide a device number, then data · alive signal · commands | `XM_CanAttachDevice` · `XM_CanReadLatest` · `XM_CanSend` · `XM_CanIsConnected` · `XM_CanGetStats` |
| Free send and receive — just an ID and data | `XM_CanSendFrame` · `XM_CanReadFrame` · `XM_CanSubscribe` · `XM_CanReadLatestById` |
| Classic CAN mode | Write `XM_CanBusMode()` in your code and return `XM_CAN_BUS_CLASSIC` (1 Mbit/s by default) — the sensor hubs do not work then |
| Sync signal · XM10 heartbeat | `XM_CanEnableSync` · `XM_CanEnableHeartbeat` |

- The default bus is CAN-FD 1 Mbit/s / 5 Mbit/s, sample point 75 %. Do not connect classic devices and CAN-FD devices together on one port.
- The XM10 board has a 120 Ω termination resistor on the CAN-FD #2 side. Put one at the device end.
- You can register up to 4 devices. For the device number, use 1 – 127 except the reserved numbers and the sensor hub numbers (`XM_CanIsDeviceIdAllowed()`).
- Details: [CAN Communication](../api-reference/11-canbus.en.md) · [`xm_api_canbus.h`](../api-reference/ref/xm-api-canbus.en.md)

## Working with CANopen Devices (Rev 2.0)

Work with a CANopen (CiA 301) motor driver in classic CAN mode.

| Feature | Functions |
|------|------|
| NMT | `XM_CanOpenSendNmt` |
| Heartbeat monitoring (up to 8 nodes) | `XM_CanOpenWatchNode` · `XM_CanOpenGetNodeState` · `XM_CanOpenGetBootupCount` |
| SDO expedited read · write (4 B or less, one at a time, no waiting) | `XM_CanOpenSdoRead` · `XM_CanOpenSdoWrite` · `XM_CanOpenSdoGetResult` |

- If the SDO response does not come within 500 ms, it is a timeout, and no new request is accepted for the next 1.5 seconds.
- For 1 kHz commands, set up the PDOs with SDO, then use PDO and SYNC (Ex.47).
- **Make the driver stop by itself if communication drops** — making the driver watch the XM10 heartbeat (`XM_CanEnableHeartbeat`) with its heartbeat consumer is the key to a safe stop.
- Details: [Working with CANopen Devices](../api-reference/12-canopen.en.md) · [`xm_api_canopen.h`](../api-reference/ref/xm-api-canopen.en.md)

- [Ex.47 CANopen Drive PDO](https://github.com/AGR-AIFT/phai-x1-xm10-release/tree/Develop/examples/47_CANopen_Drive_PDO/) — Change the PDO mapping and command at 1 kHz in time with SYNC.

## IMU Hub Sensor Calibration (Rev 2.0)

Calibrate the sensors of an IMU Hub connected over CAN-FD while they stay mounted in a case or clothing. No function waits.

| Function | What it does |
|------|------|
| `XM_ImuCalibStart(channel, item)` | Start — call it **only once** |
| `XM_ImuCalibGetStatus(channel, &status)` | Check the state |
| `XM_ImuCalibFinish` · `XM_ImuCalibAbort` | End the moving phase (save) · abort |
| `XM_ImuCalibQuerySupported` · `XM_ImuCalibGetSupported` | The items each channel supports |

- Items: gyro zero · magnetometer · simple accelerometer · full accelerometer. The MTi-630 supports only the gyro zero and the magnetometer.
- You cannot start in control mode (`XM_CTRL_CONTROL`). While a channel is being calibrated, its `XM.status.imu_hub.connected_mask` bit is off, so do not control with that channel's values.
- If you abort an EBIMU magnetometer or full accelerometer calibration, or its moving time runs past the limit, the power of all channels goes off for about 2 seconds and then comes back.
- **The IMU Hub firmware must have the calibration feature.** With old firmware, the calibration ends with "not supported" or "no response".
- Details: [IMU Hub Sensor Calibration](../api-reference/13-imu-calibration.en.md) · [`xm_api_imu_calib.h`](../api-reference/ref/xm-api-imu-calib.en.md)
- Example: [Ex.48 IMU Hub Calibration](https://github.com/AGR-AIFT/phai-x1-xm10-release/tree/Develop/examples/48_IMU_Hub_Calibration/) — gyro zero · magnetometer calibration · abort with the buttons. (not yet confirmed on the board) <!-- board-check -->

> The IMU Hub is a module under internal development. To use it, please contact us at https://huphailab.com/contact.

## Total Data Is 4 Bytes Bigger (Rev 2.0)

- Total Data (`0x20`) got an `imu_hub_timestamp_b` field (the sensor times of IMU Hub sensors 3 – 5, connected over CAN-FD), so it grew from 365 B to 369 B.
- The **registration limit of struct logging, which is sent together, is 4 bytes smaller.** A struct that was sized exactly to the registration limit with Total Data turned on may be refused at registration. If it is refused, make the struct 4 bytes smaller or lower the rate.
- **PC programs** — The `xm10` tool in `Rev2.0.zip` knows the new size. PhAI Studio, which does not know the new size, may not show Total Data. In that case, view it with the `xm10` tool.
- **Rev 1.1 boards** keep Total Data as it was (365 B). Use the `xm10` tool in `Rev1.1.zip`. `pc-data-tool/` in the repository is matched to Rev 2.0 v2.10.0.

## Fixes

| What | Details |
|------|------|
| Wobbling Total Data values (Rev 2.0) | Fixed a problem in which the IMU Hub sensor time carried in Total Data (`0x20`) came twice with the same value, or skipped one, every 50 ms · 5 seconds |
| One-shot tasks (Rev 2.0) | Fixed a problem in which, after a task made with `XM_Task_CreateOneShot()` finished, deleting it (`XM_Task_Delete()`) or stopping and restarting it touched memory that had already been freed |
| `XM_SetChannelLedRGB(ch, 0, 0, 0)` (Rev 2.0) | As documented, that channel goes back to the system's automatic display. Before, it stayed off — **code that used 0,0,0 as "off" now behaves differently** |
| Release build configuration (Rev 2.0 SDK) | Fixed a problem in which the build failed because headers could not be found when you changed the build configuration to Release in STM32CubeIDE |
| Names that `xm_api.h` pulls in (Rev 2.0) | Fixed a problem in which internal names were pulled in too, so using the same name in your code (for example a state or communication constant name) might not build. In exchange, code that used internal functions or macros that happened to be visible through `xm_api.h` may now fail to build — switch to the XM API declared in the headers. Standard functions such as `snprintf` and `abs` can still be used as before |

## Compatibility

| Item | Notes |
|---|---|
| Existing firmware code (Rev 2.0) | Mostly **just rebuild.** Check the following — code that used `XM_SetChannelLedRGB(ch, 0, 0, 0)` as "off" · a struct sized exactly to the registration limit with Total Data turned on · code that used names not declared in the headers |
| New headers | `xm_api.h` now pulls in `xm_api_canbus.h` · `xm_api_canopen.h` · `xm_api_imu_calib.h`. If you defined your own names starting with `XM_Can` · `XM_CAN_` · `XmCan` · `XM_CANOPEN_` · `XM_ImuCalib` · `XM_IMU_CALIB_` · `XmImuCalib`, they may clash |
| Rev 1.1 | **Same as v2.8.1** — `Rev1.1.zip` is the same file as v2.8.1. The Release build configuration fix is only in the Rev 1.1 SDK in the repository, not in the ZIP |
| PC data tool | Use the `xm10` tool in `Rev2.0.zip` for Rev 2.0 and the one in `Rev1.1.zip` for Rev 1.1 |
| PhAI Studio | If it does not know the new Total Data size, Total Data may not show — view it with the `xm10` tool then |
| IMU Hub | Sensor calibration needs IMU Hub firmware that has the calibration feature |
| Bootloader · KIT H10 | Bootloader v1.1.0 and KIT H10 v2.4.0, unchanged |
