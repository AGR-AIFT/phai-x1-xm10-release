# XM10 Extension Module SDK v2.2.2

> **Release date**: 2026-05-20 | **Target HW**: Rev 1.1 / Rev 2.0 | **KIT H10 FW**: v2.3.0+

---

## At a Glance

**This is a patch release focused on cleaning up example code across the SDK.** Every one of the 47 examples was reviewed line by line to fix confusing patterns and sloppy buffer/sign handling. In addition, Ex.36 (OnDevice Kinesthetic Learning) now carries a clear Rev 2.0-only notice at every relevant entry point, since it does not build on Rev 1.1.

- Code cleanup in 9 examples (Critical 3 / High 3 / Medium 4)
- Consistent **Rev 2.0-only** notice for Ex.36 in 4 locations: source header / README / tutorials roadmap / troubleshooting
- Build sweep verified: 47 / 47 (Rev 2.0) · 46 / 47 (Rev 1.1, Ex.36 excluded)
- Build environment, API, and KIT H10 firmware are identical to v2.2.1 — just download and replace

**Existing user code continues to work as-is.** No API or behavior changes. If you are already working through v2.2.1, there is no urgent reason to upgrade; if you are starting fresh, use this ZIP.

## Example Code Cleanup — 9 Changes

These are patterns that commonly trip up users when they copy example code. Even as a minor patch, they were worth collecting into a release.

### Critical — Patterns to avoid copying as-is

- **Ex.31 (Friction_Comp_DOB)** — `MAX_TORQUE_NM` was `#define`d twice in the same file (`8.0f` followed by `5.0f`), causing a compiler `redefined` warning. The effective clamp was `5.0f` as intended, but the comment above pointed to `8 Nm`, leaving users wondering why the torque never reached 8. **Consolidated to a single `5.0 Nm` definition.**
- **Ex.08 (CDC_Sensor_Print) · Ex.13 (Resistive_Mode)** — Both used bare `sprintf(...)` into a 64-byte stack buffer. If the format string grows, this silently overflows the stack. **Replaced with `snprintf(buf, sizeof(buf), ...)`**. Ex.08 is the go-to reference for CDC debug printing, so users are especially likely to copy it verbatim — hence the higher priority.

### High — Works, but confuses users

- **Ex.15 (Inverted_Pendulum)** — Negative signs were dropped in the debug serial output for fixed-point values. For example, `theta = -0.35` would print as `0.35`, making it impossible to tell from the log whether the pelvis was tilting left or right — a real obstacle when tuning PD gains. **Fixed by separating the sign as a `%s` prefix** so `-0.35` prints correctly.
- **Ex.33 (Kinesthetic_Teaching)** — The playback index advance timer reused a "loop-count macro" as a "millisecond threshold." Both happened to equal `10`, so it worked by coincidence, but changing either value would silently break the other. **Introduced a dedicated `REPLAY_STEP_MS = 10U` macro** to separate the two meanings.
- **Ex.36 (OnDevice_Kinesthetic_Learning)** — When re-entering the TSM `Active` state, the `s_mode_lost_tick` watchdog could carry a stale value, causing an immediate fallback to `STANDBY` on the very first cycle. **Added an explicit reset in `Active_Entry`**. Also added header comments explaining the multi-word volatile limitation between the background learning task and the foreground control loop — so that the question "why does Ex.38 use a mutex but this one doesn't?" has a visible answer in the code.

### Medium — Patterns that may mislead readers

- **Ex.22 (CPG_Oscillator)** — The AFO frequency adaptation formula used `sin(φ)` evaluated *after* the phase advance, which is one step ahead of the documented Ronsse 2011 formula (which uses `φ[k]`). **Pre-computed `sin(φ[k]) / cos(φ[k])`** so that both update equations reference the phase at the same point in time.
- **Ex.24 (Virtual_Constraint)** — The 5th-order Bézier basis called `powf` 12 times per 1 kHz loop iteration. **Replaced with a chained multiply sequence (`s2 = s*s`, `s3 = s2*s`, ...)**, eliminating all `powf` calls and reducing the cost to approximately 14 multiplications.
- **Ex.26 (ILC)** — The function is called once per gait cycle, not every millisecond, but the header gave no indication of this. Users could easily assume that the USB send inside was running at 1 kHz. **Added a header comment stating the call frequency (≈ 1 Hz) and guidance for moving the call to a different rate.**
- **Ex.16 (TinyAI Sensor_Fusion)** — The NN raw logit was multiplied by `× 100.0f` and printed with a `Conf:%` label, making it look like a probability percentage even though no softmax was applied. **Changed the label to `Score:`, removed the `× 100` scaling**, and added a header comment noting that this is a raw logit value.

### Ex.36 (OnDevice Kinesthetic Learning) is Rev 2.0 only — marked in 4 places

Ex.36 uses the Internal Flash UserNV API (`XM_UserNV_Read/Write/Erase`) to persist learned NN weights across power cycles. This API is **included only in the Rev 2.0 `libXM_Lib.a`**, so building on Rev 1.1 fails at link time with `undefined reference to XM_UserNV_*`.

Previously, neither the code nor the documentation disclosed this, leaving Rev 1.1 users stuck at Ex.36 with no obvious explanation. This release adds a consistent notice in 4 places.

| Location | Content |
|----------|---------|
| `examples/36_OnDevice_Kinesthetic_Learning/ondevice_kinesthetic_learning.c` header | `@warning Rev 2.0 only` + root cause + alternative for Rev 1.1 users (examples up to Ex.35) |
| `examples/36_OnDevice_Kinesthetic_Learning/README.md` top | 🛑 Rev 2.0-only notice banner |
| `docs/troubleshooting.md` new section | `undefined reference to XM_UserNV_*` — symptom / cause / resolution |
| `docs/tutorials/README.md` 47-example roadmap | "Rev 2.0 only" note on the Ex.36 row |

> If you have a Rev 1.1 board, Ex.35 (Multi-Layer Transparent Control) is the final example for your board. If you want to study just the NN training and LQR portion of Ex.36, you can temporarily remove the BTN1 long-press (Flash save) path and run entirely from RAM as a learning exercise.

## Side Note — Build Sweep Tool

`tools/build_all_examples.sh` has been added to the internal verification repository. The script swap-builds all 47 examples one at a time, substituting each into the user code area, and records PASS / FAIL, `.text` size, and failure logs automatically. This tool was the verification backbone for the code review round behind this release, and will serve as the regression test entry point for new examples going forward. (Not included in the user-facing SDK ZIP — internal verification tool only.)
