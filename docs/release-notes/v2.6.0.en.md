# XM10 Extension Module SDK v2.6.0

> **Release date**: 2026-08-20 | **Target HW**: **Rev 1.1 · Rev 2.0 (both)** | **KIT H10 FW**: v2.3.0+

---

## At a glance

This is a **safety release**. Rather than adding features, it makes the board **stop reliably when you tell it to, and recover on its own when it hangs.** The changes come out of a full re-read of the firmware from scratch.

- **Turning control off actually turns it off** — previously, going back to `MONITOR` could leave the last torque command latched on the H10 side. The firmware now ramps torque down to zero, confirms zero, and only then stops transmitting.
- **The board restarts itself if the firmware hangs** — a hardware watchdog (about 8 seconds) was added, along with fixes that keep a failed boot from turning into an endless reboot loop.
- **15 examples are safer** — soft-start on entry so nothing jumps, derivative kick removed so button presses no longer jolt the leg, and a stop when a sensor goes stale.
- **`forwardVelocity` is fixed** — it was reporting **60× too large**. If you used this value, please read [Compatibility](#compatibility).
- **Time-sync with external equipment (Ext_Sync)** — the TTL signal from an external sync box is now carried in the live data stream, so you can see exactly which span was being recorded.

> **For Rev 1.1 users**: this is the **first update to reach Rev 1.1 since v2.5.0** (v2.5.1 was Rev 2.0 only). Everything above applies to Rev 1.1 as well.

## 1. Turning control off actually turns it off

### What was wrong

XM10 works by **continuously sending torque commands** to the H10. The H10, in turn, **holds the last command it received** if new ones stop arriving — a deliberate safety behavior so the robot does not drop out the instant a cable glitches.

That is where the problem was. Calling `XM_SetControlMode(XM_CTRL_MONITOR)` made XM10 **stop transmitting immediately.** From the H10's point of view, the last command — a non-zero torque — was still in effect. **You thought you had switched it off, but torque was still applied.**

### How it works now

Returning to `MONITOR` now goes through **three stages**:

1. **Ramp down** — torque decays exponentially from its last value to zero, and keeps transmitting while it does (time constant 0.1 s).
2. **Confirm zero** — zero torque is sent several times over, so a single dropped frame cannot leave a stale value behind.
3. **Release vectors** — if P/I vectors were in use, their release commands go out too. Only then does transmission stop.

The whole sequence normally takes **0.3–0.6 s**.

### When you need to stop *now*

If there is no time even to ramp down, call **`XM_EmergencyDisengage()`**. It skips the decay stage and confirms zero immediately.

```c
if (something_is_wrong) {
    XM_EmergencyDisengage();   // no ramp, straight to zero
}
```

### Seeing the actual state

`XM_SetControlMode()` is a **request**; because of the three stages above, the state actually in effect can briefly differ. Read the real state with the new call:

```c
XmAppliedMode_t m = XM_GetAppliedControlMode();
// XM_MODE_APPLIED_CONTROL     — control output active
// XM_MODE_APPLIED_MONITOR     — output blocked
// XM_MODE_APPLIED_TRANSITION  — switching (your torque commands are ignored meanwhile)
```

> **MONITOR is now a complete block.** In `MONITOR`, **no control command of any kind leaves the board** — neither torque nor vectors. Use it freely to run an algorithm and just watch the numbers.

## 2. The board restarts itself if the firmware hangs

A **watchdog** forces a reboot unless the firmware regularly checks in. XM10 now has a hardware watchdog (IWDG) set to about **8 seconds**, refreshed at 1 kHz by the task that runs your `Control_Loop`.

Fixed alongside it:

- **No more endless reboot loops** — a failure during startup used to reboot, fail again, and reboot again. Now a **startup failure halts in place** so you can inspect it, and the watchdog only restarts the board for a hang that happens **during normal operation**.
- **Boot breadcrumbs** — how far the boot got, and why the last reset happened, are recorded in memory. You can narrow down a problem without having to reproduce it.

> ⚠️ **A watchdog is not an emergency stop.** If your code keeps running while commanding the **wrong torque**, the watchdog never fires — as far as it can tell, the firmware is perfectly healthy. In wearer trials, **a person stopping the suit** is still the primary safety net; see [Wearable Safety](../safety/wearable-safety.en.md).

> ⚠️ **If you create your own tasks**: a task that runs at a higher priority than `Control_Loop` and **holds the CPU for more than 8 seconds will reset the board.** Yield periodically with `XM_Task_Sleep()`. (See [Task Creation Guide](../api-reference/09-task-creation.en.md) §4.)

## 3. The examples are safer

Fifteen examples had their safety handling reworked. **Example numbers and what they teach are unchanged.**

| What | Which examples | Why |
|---|---|---|
| **Soft-start on entry / slew limiting** | Ex.14 · 21 · 27 · 30 · 33 | Removes the jolt when assist turns on and torque snaps from 0 to target |
| **Derivative kick removed** | Ex.14 | A step change in the setpoint used to blow up the D term. The derivative is now taken on the **measurement** instead of the error, which removes the cause outright |
| **NC stop switch handling · output clamps · stop ramps · stale-sensor timeouts** | Ex.06 · 13 · 17 · 26 · 32 | A broken switch wire now reads as "stop"; a spiking value can no longer exceed its limit |
| **Mode-transition consistency · fail-closed homing** | Ex.11 · 12 · 15 · 35 · 36 | Blocks the path into control while homing has not completed |
| **Double unit conversion removed** | Ex.11 · 12 · 15 · 35 · 36 | Cleans up places that converted current (A) to torque (Nm) twice |

Separately, **Ex.03 · 08 · 31 · 37** only had their prose corrected (no behavior change) — a stale filename (`user_app.c`), a comment saying `sprintf` where the code already used `snprintf`, a log string, and the torque-unit explanation in Ex.31.

### Bench-operation guidance added

**Ex.15 · 21 · 30 · 33** were tuned assuming **a person is wearing the suit**. Run them on the bench, with the leg hanging free, and the much lower inertia makes them **oscillate or diverge** — the example is not broken.

Each of those files now carries a **bench-parameter comment** at the top. Substitute the link's own mass and center-of-mass values (0.184 kg / 0.1264 m) and they behave predictably on the bench.

## 4. `forwardVelocity` is fixed ⚠️

`XM.status.h10.forwardVelocity` was reporting **60× the real value** — the per-minute → per-second division was missing from the unit conversion.

- **If you only displayed it** — it now shows sensible magnitudes. Nothing to do.
- **If you fed it into control** — you may have compensated with a very small gain. **Re-tune that gain.**
- **If you have previously recorded data** — its `forwardVelocity` is the 60× value. **Do not mix it with new data.**

## 5. Time-sync with external equipment (Ext_Sync)

XM10 can now read the **TTL output of an external sync box** on external GPIO **DIO 8** and carry it in the live data stream. In PhAI Studio you can see **exactly which span was being recorded**, on the same timeline as the XM10 data.

Three channels were added to Total Data:

| Channel | Meaning |
|---|---|
| `sync_save_active` | **1 = recording** — this is the one to use |
| `sync_din_level` | Current electrical level on the pin (diagnostic) |
| `sync_din_edge_count` | Total number of transitions (cross-check for missed events) |

**You do not have to care about polarity.** A sync box flips its output polarity from its own button, so whether "recording" means HIGH or LOW can differ from day to day. XM10 **latches the level it reads at boot as the idle state** and treats any deviation from it as recording. Either polarity works.

> **Just keep the connection order.** ① Leave the sync box **not recording** (orange LED off), ② power up XM10, ③ from then on **do not press the sync box button** — electrically it produces exactly the same waveform as a save signal, so nothing downstream can tell them apart. Drive recording only from the tablet app.

Wiring: sync box TTL output (0/3.3 V) → **DIO 8** (`XM_EXT_DIO_8`) on the XM10 external GPIO header, common GND. For the physical pin, see [External IO](../api-reference/04-external-io.en.md) and the pinout page for your board.

> **If you were already using DIO 8.** The system claims this pin as an input (pull-down) at boot. That happens **before** `Control_Setup`, so if you reconfigure it there with `XM_SetPinMode(XM_EXT_DIO_8, ...)`, **your setting wins.** Existing code keeps working; the three channels above simply become meaningless.

## New APIs

| API | Purpose |
|---|---|
| `XM_EmergencyDisengage()` | Skip the ramp-down, confirm zero torque immediately |
| `XM_GetAppliedControlMode()` | Read the **actually applied** control mode, not the requested one |
| `xm_api_safety.h` (header-only) | Shared safety helpers — `XM_SafeTorque_*` (limit + slew), `XM_SafeAssistLevel()`, `XM_SafeIsFresh()` (sensor freshness) |

`xm_api_safety.h` is already pulled in by `xm_api.h`, so no extra `#include` is needed.

```c
static XmSafeTorque_t s_safe;

void Control_Setup(void) {
    /* limit 2.5 Nm | at least 500 ms from 0 to the limit (slew; 0 = unlimited)
     * | 500 ms soft-start on entry */
    XM_SafeTorque_Init(&s_safe, 2.5f, 500U, XM_SAFETY_DEFAULT_RAMP_MS);
}

void Control_Loop(void) {
    /* finite check -> clamp -> soft-start -> slew limit, in one call */
    float t = XM_SafeTorque_Step(&s_safe, my_desired_torque);
    XM_SetAssistTorqueRH(t);
}
```

When you switch control off and back on, call `XM_SafeTorque_Reset(&s_safe)` to restart the soft-start. `XM_SafeTorque_Step()` must be called **exactly once per tick** in `Control_Loop` for its timing to be correct.

**The bootloader was updated.** One thing is new this time:

- **Self-recovery from a corrupted config area** — if the bootloader's configuration area was damaged (by a power fault, for example), reading it raised an error and the board would not boot at all. That case is now detected: the configuration is reset and boot continues.

> The "clear pending system interrupts on the jump to the application" fix that shipped with the v2.5.1 attachment is already in this build. If you installed the v2.5.1 bootloader, you keep that and gain the item above.

**v2.6.0 firmware runs fine on the older bootloader.** This update guards against a *board-will-not-boot* situation, so it is **recommended, not required** — reinstall it over SWD when convenient; see [Bootloader Upload](https://github.com/AGR-EXO/Extension_Module/blob/v2.6.0/docs/bootloader/README.md). **KIT H10 firmware and content files are unchanged**, so if you have already installed those, there is nothing more to do.

The final build step (producing the uploadable `.bin`) uses **Python**. If you have not installed it, follow [Software Setup](https://github.com/AGR-EXO/Extension_Module/blob/v2.6.0/docs/getting-started/02-software-setup.md) to install Python 3.10+ (adding it to PATH is required).

## Compatibility

| Item | Impact |
|------|--------|
| Your code (`Control_Setup` / `Control_Loop`) | **Just rebuild** — nothing was removed. The older name `XM_CTRL_TORQUE` still works |
| `XM_SetControlMode(XM_CTRL_MONITOR)` | **Behavior change** — it now ramps down over 0.3–0.6 s instead of cutting off instantly, and your torque commands are ignored during that window. For an immediate stop use `XM_EmergencyDisengage()` |
| `MONITOR` mode | **Behavior change** — torque **and** vectors are now fully blocked |
| `XM.status.h10.forwardVelocity` | **Value change (60× correction)** — code that used it needs re-tuning; do not mix old and new recordings |
| Your own tasks | **New constraint** — holding the CPU for over 8 seconds triggers a watchdog reset |
| External IO `DIO 8` | **Claimed by the system at boot** as an input (Ext_Sync). Reconfiguring it in `Control_Setup` wins — existing code is unaffected |
| Total Data packet | **Same size (365 B)** — the three Ext_Sync channels went into previously reserved bytes. Nothing after them moved, so **existing receiver programs keep working unchanged** |
| PhAI Studio | Works as before — pick up the three new channels if useful, ignore them otherwise |
| KIT H10 firmware / content files | **Unchanged** — no update needed |
| Bootloader | **Updated** — reinstall over SWD recommended |
| Example count | Unchanged (Rev 2.0: 45 · Rev 1.1: 42) |
